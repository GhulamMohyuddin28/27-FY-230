## 9. Short Answers

### 1. Why is 100% code coverage not necessarily meaningful?

100% coverage does not automatically prove that the tests are useful. Tests must check actual behaviour and expected results, not merely execute every line of code.

### 2. What was the coverage result, and which lines were uncovered?

For `tools/build.js`, line coverage was 94.44%, branch coverage was 83.33%, and function coverage was 100%. Lines 35–36, related to the CLI entry point, were uncovered.

### 3. Why should all pipeline stages be required?

All required stages protect the main branch. If a required stage fails, the pull request should not be merged.

### 4. What does `sonar.qualitygate.wait=true` do?

It makes the SonarQube scanner wait for the quality gate result and return a failure when the quality gate fails.

### 5. Why is the coverage report uploaded as an artifact?

GitHub Actions jobs run on separate fresh runners. Uploading the coverage file allows the analysis job to download and use the report generated by the test job.

### 6. Why did SonarQube detect the duplicate comparison?

SonarQube detected that both sides of the comparison used `pageA.title`. Earlier ESLint rules did not detect this specific logical mistake, and the original tests did not adequately check different page titles.

### 7. Why did the coverage condition not fail the small change?

According to the lab instructions, the coverage and duplication conditions are not applied to changes below 20 new lines.

## 10. Conclusion

This lab demonstrated how to create a staged CI pipeline, test code coverage, enforce linting, integrate SonarQube Cloud, and protect the main branch using required checks and Code Owner reviews.

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
  schedule:
    - cron: '0 2 * * *'         # 02:00 UTC, nightly

jobs:
  lint:
    name: lint
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: make lint

  test:
    name: test
    needs: lint
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: make coverage
      - uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/lcov.info
          if-no-files-found: error

  analyse:
    name: analyse
    needs: test
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/download-artifact@v4
        with:
          name: coverage
          path: coverage
      - uses: SonarSource/sonarqube-scan-action@v8
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

  package:
    name: package
    needs: [test, analyse]
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: make package
      - uses: actions/upload-artifact@v4
        with:
          name: devops-pipeline
          path: '*.tgz'
          if-no-files-found: error

  audit:
    name: dependency-audit
    runs-on: ubuntu-24.04
    if: github.event_name == 'schedule'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npm audit --audit-level=high
```
